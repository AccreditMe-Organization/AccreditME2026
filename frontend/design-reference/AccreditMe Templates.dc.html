Filter panel — how it opens
One Filters button with a count, opening a right-side sheet, not a dropdown: three or more filters cannot be laid out in a panel that must not scroll, and a sheet is its own layer with no scrollable ancestor. Inside it, each filter is a labelled control from artboard 6, Apply and Reset in a fixed footer, and the applied set returns to the toolbar as removable chips. Single-axis lists (Status) stay as inline segmented chips in the toolbar — cheap, visible, no layer at all.
Relation in a cell
Org unit is a relation, so it renders as the artboard-4 field in its table variant: no type glyph (the header names the type), one line, ellipsis, full value in title, and the three access states rendered in place so the column never goes ragged. Row 5 below shows named and row 6 hidden.
No zebra, and why
Rows are separated by a 1px #F0F3F7 rule, not alternating fill. Zebra spends the one background channel the row has, and that channel is needed for hover (#F2F7FB), selected (#E4EEF6) and the overdue tint. Keyboard focus is the 2px ring on the row, which is focusable and moves with ↑/↓; Enter opens the record, Space selects.

Settled: tabs versus filters
My Tasks today has raw PENDING / IN_PROGRESS tabs, none selected on arrival, and cancelled rows with no tab to reach them. The rule: tabs are for disjoint scopes of the same object that a user switches between as a mode; filters are for narrowing one scope. Task state is a filter, not a mode — so My Tasks gets no state tabs. It opens on a default saved view (“Open, mine, soonest first”), with status as segmented chips in the toolbar including Cancelled, and every chip carries a count so an empty scope is visible before it is chosen. A list may never open with no view selected: the default view is part of the route.
Saved views and persistence
Sort, filters, page size, density and column choice persist per user, per list, and are also encoded in the URL so a filtered view can be pasted to a colleague or cited as evidence — a surveyor sees exactly the set that was referenced. “Save this view” names it and pins it to the list's header as a chip row; one view per list may be marked default. Clearing filters never clears the saved view; leaving the page never loses it. Admins can publish a view to a role, which is how the seven configuration lists get sensible defaults without eighteen bespoke screens.

The cap measurement, and the rule applied

Finding — four chains do not survive as stacked sections
Four artboard-11 groups as four stacked sections measures roughly 1,150px, puts four Save buttons on one page, and — the real defect — makes the only question an administrator actually has unanswerable: does escalation get faster as priority rises? That is a comparison across the four chains, and stacking hides it. So the section becomes a per-priority matrix: one row per priority, the chain laid out along it, limit in the column beside it. Each row is still a full artboard-11 group — handle, stepper, target select, named remove, add with its allowance, maximum 4 — but they share one header, one problem count and one Save, because they are one policy, not four. Reading down the target column shows the ladder rising; reading down the day column shows it tightening. A stacked layout would need four scrolls to learn the same thing. The matrix scrolls horizontally below 640px rather than reflowing, since a chain that wraps mid-step is worse than a scroll. This changes template 5: a settings section whose repeating groups differ only by one key takes the matrix form, not the stack — the stack stays correct for sections that are genuinely unrelated decisions.

The save model, and why it is not a page Save
A matrix has no natural sections to save, and 200 cells cannot be autosaved — a mis-click would grant approval rights to fourteen people silently. So: cells change locally and mark themselves, a running count sits in the header, and the primary action is Review n changes…, which opens a confirm dialog listing every change in words (“Incidents · Approve: granted”, “Lookups · Delete: revoked”) with the affected user count. Save writes them as one transaction. This is the second of the two route-guarded screens. Cap sizing — measured from the tallest combination
The stage editor's worst case is Fixed position × Parallel: identity row 77 + axis 1 (selector 77 + two dependent pickers 172) + axis 2 (selector 77 + threshold 77) + the live-records warning 56 = 536px. That is 116px over the 420px cap — a diagnostic comparison, not a violation, since the cap governs DIALOG bodies and a page panel has none to defend — so the stage editor is not a dialog — it is the panel beneath the flow strip on /workflows/:id/stages, where there is no cap to defend and both axes are visible at once. The transition editor measures 604px with three action rows and is the same: a page panel, not a dialog. Both keep the pattern-10 fixed slots regardless, because the reason for them — the footer never moving under the cursor when a kind changes — applies on a page too.
The page scrolls as the document — no inner scroll container
Moving both editors out of a dialog was right on the cap arithmetic, but it also moved them out from under artboard 7's protection — and both are full of selects and pickers. So this is a build constraint, not a preference: /workflows/:id/stages scrolls as the document. No overflow: auto wrapper around the flow strip, none around the editor panel, no fixed-height column with the editor inside it. The flow strip may scroll horizontally — that axis fires no vertical scroll handler — but nothing on this route may scroll vertically except the document. If an inner scrolling region is ever introduced here, every select in both editors reintroduces the exact platform fault artboard 7 exists to make unreachable, and it will present as “the stage editor's dropdowns close when I scroll”. The overlay guard from artboard 7 catches it in development; this note exists because the current build already has pages with inner scroll containers, so the pattern is available to copy by accident.
Two axes in one form — why it holds
Each axis gets its own bordered card with its own kind selector and its own fixed slot, so a change on one cannot move the other. They are labelled by the question they answer — “who the work lands on”, “how approval is reached” — rather than by their schema names, because assigneeStrategy and approvalMode sound interchangeable and are not. The one place they interact is stated in copy, not structure: Committee approval mode with a non-Committee assignee strategy is a valid but unusual pair, and the form says so inline rather than silently forbidding it. Read-only rendering names both kinds — “Assignee · Fixed position · Quality Manager in Quality & Patient Safety” and “Approval · Parallel · Majority”.

Why a picture and not nested tables
A workflow is a graph, and the single question an administrator asks of it — “can a record get from here to there, and who sends it?” — is unanswerable from a table of rows. The flow strip answers it in one glance: stages left to right in order (right to left in Arabic), forward transitions as solid connectors, returns as dashed ones, and the live record count in each stage, which is the number that tells you how risky an edit is. It is not a free canvas: no dragging, no arbitrary positions, no layout to maintain — a linear strip with return arcs, generated from the data, which is all these workflows actually are. Selecting a stage or a connector opens its editor beneath; nothing is edited in the picture itself.

Bell versus Setup health — the division holds
The bell carries events: something happened, you read it, it ends. Setup health carries conditions: derived state, recomputed every fifteen minutes, with no read flag and nothing to dismiss. Why the “a task is not a record” argument fails
The case against was that a task is a work item — transient, owned by a list, complete when ticked. That held while a task was a title, an assignee and a date. It no longer does: a task now carries a description a surveyor reads as the statement of work, evidence attached on completion, an SLA chain with escalations that have already fired and were sent to named people, a delegation label, and a source relation to whatever raised it. Three of those five are audit evidence, and the single question a surveyor asks — “show me this action was taken, by whom, and what proves it” — cannot be answered by a row in someone's list. GET /tasks/:id already exists, so the route is not new work; leaving it undesigned only meant every notification landed on a list with the row highlighted, which is the weakest thing in the product today.
