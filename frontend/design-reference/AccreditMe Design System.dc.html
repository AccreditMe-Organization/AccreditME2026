Where we disagree with the current build
A workflow stage is not a status and must stop looking like one. A stage is a position in a known sequence — it is only meaningful with the sequence attached, which is why the chip carries n/total and why the full stepper lives in the record header. “Terms Review” alone tells a reader nothing about whether that is early, late, or a regression. Status, by contrast, is a closed set with an expected member, so the expected member gets no decoration at all. Severity is the only one of the three that asserts someone must act, so it is the only one allowed a fill — and a severity chip without a consequence sentence beside it is incomplete.

Dialog geometry — one shape, three sizes
{{ d.name }} {{ d.spec }}
Header and footer never scroll. If content with all pickers open exceeds the body cap, the interaction is not a dialog — it becomes a stepped dialog or a page. This is the rule that makes the platform limitation unreachable: no dialog body ever both scrolls and contains a picker.
Overlays that are still allowed
Only through the CDK overlay with a reposition scroll strategy. Toolbar filters and the column chooser may stay floating panels only when mounted via our existing OverlaySelectComponent route — never a raw p-select or p-overlaypanel. PrimeNG's ConnectedOverlayScrollHandler dismisses on any ancestor scroll event, whether or not the trigger moved, so a position: sticky toolbar does not save it — reposition-on-scroll does.
Row action menus. Short, no nested picker, and re-opening costs one click — a scroll-close here is a nuisance, not a dead end. They may use the default handler and close on scroll.
Never inside a dialog body, and never a raw overlay inside a scrolling panel body (the compact list panels). Those get inline expansion or a picker dialog instead.
Stated as an engineering rule: the overlay component refuses to mount inside a scrollable ancestor unless it is using the reposition strategy, and throws in development when it is not. The earlier phrasing — refuse any scrollable ancestor but the document — would have rejected a legitimate toolbar overlay on every page whose list scrolls in a container. A rule that only lives in a document gets broken on the eleventh screen; this one fails the build.

Switching kinds after values are entered
Fields that exist in both kinds and mean the same thing keep their values — matched by name and type, declared in the variant map rather than guessed. Fields belonging only to the old kind are held in session memory, not destroyed: switching back restores them with no prompt, which is what makes exploring the kinds free. Switching kinds is therefore never destructive and never confirmed — a prompt warning about values that are demonstrably restorable only teaches users to click through prompts. The single discard is on submit: only the active kind's values are sent, and the held memory goes with the form.
Write-once secrets — a system rule, not a screen's problem
Any secret (a webhook signing secret, an API key, an SMTP password) is entered once and never rendered again. Empty state: a password-type field with “Paste the signing secret”. Once set: the field is replaced by the read-only pair “Secret · set 14 Sep 2026” with a single Replace text button that reopens an empty field, and a Remove in the row menu. No reveal control, no masked placeholder pretending to hold the value, and the value never appears in an export, a tooltip or the audit trail — the trail records “secret replaced by N. Al-Otaibi”, not the secret.

· {{ s.k }} {{ s.v }}
What happens to the dialog cap as rows are added
This is where a capped body breaks, so the answer is explicit. A group whose maximum is three rows may live in a dialog: the cap is sized for three rows plus the add button, and the Add button disables at the maximum with the reason beside it. A group whose maximum is four or more does not belong in a dialog at all — it belongs on a page or in a wizard step, where there is no cap to defend. The escalation chain (max 4) is therefore a settings-page group; a transition's actions (max 3 per transition) are a dialog group. The one thing never permitted: a group that scrolls inside a capped dialog body. It would put selects and pickers inside a scrollable ancestor, which is exactly the platform fault artboard 7 exists to make unreachable.

The rule that falls out of the arithmetic
A dialog may hold an open inline calendar plus at most one other field, and that field may not carry a persistent helper line. 420 − 258 − 8 − 75 leaves 79px, which is one compact field block and nothing else. Anything richer is not a dialog: it belongs on the page it configures (preferred wherever a settings page already exists) or becomes a stepped form with the date alone on its own step. So on a step that has other fields, the calendar substitutes for them rather than pushing them down: pressing ▢ swaps the step's body for the date-and-time view above, with a “← Back to details” link, the same dialog header and the same footer. Nothing floats, nothing overlays, nothing scrolls — the in-flow rule is intact; what changes is that “in flow” means instead of, not below. It is not a new wizard step: the step's values are all still live, Create is still reachable, and a user who never presses ▢ never sees it. Use this only where the presets already cover the common case; a form whose primary act is picking a date puts the calendar in flow normally.
In the substituted view the calendar is present from the start and collapses only on an explicit dismissal — a second press of ▢, Escape, or focus leaving the whole date-and-time block. It does not collapse on picking a day, because the day is usually picked before the time and snapping shut is what forced users to set the time first. There is no Done button: the value applies as it changes, and the dialog's own Save is the only confirmation. Nothing here is modal, so there is no second thing to confirm.
Named compromise · the time control is not p-calendar's
PrimeNG's hour/minute spinners are not adequate for the urgent case, and we should not pretend otherwise: reaching 18:00 from a 16:30 default is up to six presses on one spinner or a fiddly click-and-type in a two-segment control, at the moment someone is raising an incident. The fix needs no new library — it is a p-inputmask HH:mm field plus the preset row above, both plain PrimeNG. Presets are computed from now and the tenant calendar: +1h, +2h, End of working day, Tomorrow 09:00, each writing both date and time in one press, each announcing the absolute value it set. Typing remains complete and primary; the presets are the fast path, not the only one.
Out-of-hours: allowed, warned, never blocked
A hospital does not stop at 17:00. Blocking an 18:00 due time would make the product refuse to record something that is actually true, and people would round to 17:00 and quietly corrupt the SLA data we sell the platform on. So an out-of-hours time is accepted, and the warning does the one thing that matters: it converts the choice into working time, because that is the number the SLA will be measured in and the number the user has in their head is clock time. The same sentence appears on a non-working day (“Friday is not a working day…”), and on a past time, which is the only case that is an error rather than a warning.

Artboard 13

Compact dialog density

A second density for crowded dialogs — and the finding that the space is in the slots and the gaps, not in the type.
The finding
A standard field block is 75px, of which 36 is the control and 39 is label, gaps and a reserved message slot. Compact density recovers 23px of that 39 without touching a single type size.
Type size was the obvious lever and it is the wrong one. Latin label 12px is already at the floor that keeps its Arabic sibling at 13px — artboard 2's smallest readable Arabic step — so a Latin label of 11px would force Arabic to 12px, below the floor, and the two languages would then need different control heights. That is a separate RTL geometry, which this system does not permit. The 23px is instead taken from a 4px gap that can be 2, a 36px control that can be 32, a 12px field gap that can be 8, and a message slot reserved on fields that can never produce a message. The last of those is the largest single saving and costs nothing at all.

Not scaled by density: the inline calendar (28×28 cells, 258px — it sits at the WCAG target floor plus 4px, so density may never touch it), icon-button targets (32×32), and every type size. Density changes geometry around controls, never the controls' reach or their legibility.
When it applies — a measurement, not taste
Compact density is applied to a whole dialog when its standard-density body would exceed the 420px cap, or when it holds five or more field blocks. Never mixed inside one dialog — two field rhythms in one form reads as a rendering fault. Never on pages, record panels or settings sections: those are read far more than edited, they have no cap to defend, and artboard 1's form density stays the default there. It is a property the dialog declares (density="compact"), computed once from the field list at design time, so it cannot drift per screen.
The message slot rule — confirming the build's removal
Yes, that is the intended rule, with one clause added. The slot is reserved only on fields that can produce a message — anything with validation, a persistent helper line, or an async state. A required select over a closed list with a default, and a toggle, can produce none, so they get no slot. The added clause is what keeps “the layout never jumps” true: a field declares message: 'reserved' | 'none', and a field that declared 'none' may never show a runtime message. If one later needs one — a server-side conflict on Assigned to, say — it must change its declaration and pay the 17px, rather than growing a slot the first time the server disagrees. Without that clause, removing the slot just moves the jump from every form to the rare one, which is worse: it happens exactly when the user is already being told something went wrong.

Why the floating label loses on this product specifically. It is a good control and PrimeNG has it, so the objection is not taste. It saves its 20px only while a field is empty — and most dialog traffic here is editing an existing record, where every field arrives filled and every label is therefore already floated above it. The saving is largest on new-record forms, which are the ones that were not crowded. Against that: it collides with the trailing affordances our fields carry at 32px (the date field's ▢, the picker's “Change…”, the search field's ✕) because the floated label and the affordance compete for the same top-inline corner; and the float transform clips IBM Plex Sans Arabic's ascenders and diacritics inside a 32px control, so Arabic would need a taller control than English. A per-language control height is a separate RTL geometry, which is the one thing this system refuses. Keeping the label above costs 20px, buys a question that is visible while the answer is being checked — the compliance case, where someone reads a filled form aloud to a surveyor — and keeps one geometry for both languages.
Placeholder-as-label is refused outright
Three reasons, in order of weight. It fails WCAG 3.3.2, which the product is procured against as an all-or-nothing claim, and automated audits report it as a missing label — a question on a buyer's checklist, not a matter of judgement. The value then occupies the space the question occupied, so a filled form no longer says what it is a form of; on a record-editing product where the common act is checking someone else's entry, that is the exact moment the label is needed. And it does not survive artboard 8's read-only rendering, which is a label-over-value pair — a field whose label lives in its placeholder has nothing to render read-only. The 20px is real and the pressure is legitimate; it is paid for out of the slots and gaps above instead.
