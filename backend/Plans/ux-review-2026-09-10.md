# AccreditMe UX Review

_UI/UX review of the development build (localhost:4200) · 10 Sep 2026 · tenant al-nakheel, Organization Administrator · read-only_

**Findings:** 26 — 6 major, 18 minor, 2 improvement

## Summary

The foundation is solid: every Arabic string is translated, most screens use the same page-header layout, the colors are restrained, and a few pages (Transfer User, Task SLA) already show the right patterns. The gaps are in what enterprise users rely on every hour: a home page that shows their work, tables they can search and export, a task inbox they can act from, and notifications they can trust. Most findings are patterns rather than one-off bugs. Documents, Incidents, CAPA and Audit will copy them, so settle them before those modules are built.

Severity: **Major** = blocks a core task or would hurt credibility in a demo · **Minor** = friction, inconsistency or a local defect · **Improvement** = a better approach worth planning, not a defect.

## What’s working

- **Arabic is fully translated** — ar.json has all 530 keys that en.json has, none left in English, and Arabic name inputs are set to right-to-left.
- **Page headers follow one pattern** — Title on the left and primary action on the right on nearly every list page, with restrained use of the brand blue.
- **Transfer User is a proper wizard** — Destination → Position → Manager → Review, with a review step before a change that has consequences. Other high-impact changes should work this way.
- **Task SLA & Escalation is a model settings page** — A plain-language description, the four priorities side by side, and one Save.
- **Destructive actions are confirmed** — ConfirmationService is wired in throughout the frontend. I didn’t trigger any confirmations, to keep the review read-only.
- **Good empty-state wording** — “No unassigned tasks — everything has an assignee.” reassures the user instead of just reporting nothing.

## Navigation & information architecture

<a id="ux-01"></a>

### UX-01 · Major · No home page: users land on an admin configuration screen

*Where:* Post-login landing → /organization

*Observed:* After login the app opens Organization Structure, a one-time setup screen. Nothing tells a quality officer or committee member what needs their attention today. CLAUDE.md already flags that a Dashboard/Home page should come before Meeting Management.

*Recommendation:* Add a role-aware “My Work” home: my open and overdue tasks, approvals waiting on me, committees in review, and the latest notifications. Send every user there after login and when they click the AccreditMe logo.

<a id="ux-02"></a>

### UX-02 · Major · Sidebar mixes setup screens with daily work, and Settings repeats them

*Where:* Sidebar, Admin Settings hub

*Observed:* Of the 10 sidebar items, 7 are configuration (Organization Structure, Working Calendar, Lookups, Roles, Workflows, Org Positions, Users). The Admin Settings hub links to the same 7 screens again. Once Documents, Standards, Incidents, CAPA, Gap, Audit and KPI arrive, the flat list will pass 17 items.

*Recommendation:* Keep the sidebar for operational modules, grouped under headers such as Work, Governance and Quality. Move all configuration into Settings, with its own secondary navigation. Do this before Document Management lands, while there are few items to move.

<a id="ux-03"></a>

### UX-03 · Minor · Two sidebar items are highlighted at the same time

*Where:* /tasks/unassigned

*Observed:* Both “Tasks” and “Unassigned Tasks” show the active style, because the sidebar uses routerLinkActive with exact: false and /tasks is a prefix of /tasks/unassigned.

*Recommendation:* Use exact matching for Tasks, or make Unassigned a tab or filter inside Tasks rather than a separate sidebar entry.

<a id="ux-04"></a>

### UX-04 · Minor · The breadcrumb doesn’t show where you are, and back buttons are inconsistent

*Where:* All pages; detail pages in particular

*Observed:* The breadcrumb is one plain, non-clickable label that repeats the page title. Detail pages (a committee, a workflow’s stages, public holidays, lookup values, a user) still show only the parent name. Some detail pages have a ← back arrow (Holidays, Lookup values, Permission matrix) and others don’t (Workflow stages, Committee detail, User detail).

*Recommendation:* Show a real, clickable trail, e.g. Workflows › Committee Management › Stages. On top-level pages, hide either the breadcrumb or the duplicate title. Use one back pattern on every detail page.

<a id="ux-05"></a>

### UX-05 · Minor · “My Profile” opens the admin’s edit screen for users

*Where:* Profile menu → My Profile → /users/:id

*Observed:* The link opens the admin user record: it highlights Users in the sidebar and shows Transfer, Position, Manager and role assignment. Two-factor setup only appears on your own record. Users without admin rights need a self-service page.

*Recommendation:* Build a separate My Profile page with name, language, calendar display (Gregorian/Hijri), out-of-office, two-factor and notification preferences. Keep organizational fields on the admin record.

<a id="ux-06"></a>

### UX-06 · Minor · Every browser tab is titled “Frontend”

*Where:* index.html; no TitleStrategy

*Observed:* The document title never changes between pages, so users with several tabs open, or searching their history and bookmarks, can’t tell AccreditMe pages apart.

*Recommendation:* Add an Angular TitleStrategy that sets titles such as “Infection Control Committee · AccreditMe”, and replace the default favicon with the AccreditMe mark.

## Daily work: tasks, workflow, notifications

<a id="ux-07"></a>

### UX-07 · Major · Notifications are flooded with one repeated, unactionable alert

*Where:* Topbar bell and notification panel

*Observed:* There were 284 unread notifications at login, rising to 285 during the review. Every visible item is the same “Head-authority setup incomplete” alert, repeated every 15 minutes. Items don’t say which unit is affected, can’t be clicked or reached by keyboard, and there is no page to see them all. White text on the red badge measures 3.76:1.

*Recommendation:* Keep one open alert per condition and refresh its timestamp instead of adding a new one. Make each item link to the record that needs fixing, name that record in the text, and group items by type. Add a notification centre page with filters, and cap the badge at 99+. The repeat cadence is a backend change; the presentation is a UI change.

<a id="ux-08"></a>

### UX-08 · Major · The Tasks page shows tasks but doesn’t let you work on them

*Where:* /tasks (My Tasks)

*Observed:* The filter tabs show raw status codes (PENDING, IN_PROGRESS, OVERDUE, COMPLETED). No tab is selected by default, yet the list shows Completed and Cancelled tasks. There is no “All” or “Cancelled” tab and no counts, and the selected tab is barely distinguishable. Rows can’t be clicked, Source says “COMMITTEE” instead of the committee’s name, and there is no way to open or complete a task from here.

*Recommendation:* Open on an “Open” view (pending, in progress and overdue) sorted by due date. Put counts on the tabs, highlight overdue rows, and link each title to its source record. Show due dates in working-calendar terms, e.g. “Due in 2 working days”.

<a id="ux-09"></a>

### UX-09 · Minor · A record’s workflow stage is easy to miss, and its actions have no hierarchy

*Where:* Committee detail, Committee list

*Observed:* “Current Stage: Terms Review” appears as small grey text. The two transitions, “Approve Committee” and “Revise Terms”, are both styled as primary buttons. They load after the rest of the page and push it down. Committee cards in the list don’t show a stage at all.

*Recommendation:* Put a stage badge in the record header with a horizontal stage stepper (Formation → Terms Review → Active …). Style one action as primary and the others as secondary, and show the SLA due time and assignee. Reserve the header space while it loads, and add a stage chip to list cards.

<a id="ux-10"></a>

### UX-10 · Improvement · Workflow templates are edited as a table, with no picture of the flow

*Where:* /workflows/:id/stages

*Observed:* Stages are reordered with up/down arrows, and transitions sit in nested expandable rows. One column holding the “Initial Stage” and “Final Stage” badges has no header, and neither does the column of gear icons in the transitions table. The “SLA (working hours)” header wraps.

*Recommendation:* Add a read-only diagram beside the table, generated from the stages and transitions (stages as boxes, transitions as arrows). The full draw.io canvas can stay in Phase 3; a simple generated diagram already lets admins check a flow at a glance.

## Lists & data tables

<a id="ux-11"></a>

### UX-11 · Major · No table can be searched, sorted, filtered, paginated or exported

*Where:* All 18 tables in the app

*Observed:* A code scan found 18 components using p-table, with no paginator, no sortable columns, no search or filter, and no export. The Users list already has 25 people with no search box. A hospital tenant will have hundreds of users and thousands of documents and incidents. CLAUDE.md promises every table can be exported to XLSX.

*Recommendation:* Build one shared list-page pattern before Document Management: a toolbar with search, filter chips (status, type, unit), column chooser and Export; sortable headers; server-side pagination with a count such as “1–25 of 312”; and saved views later. Every module then inherits it.

<a id="ux-12"></a>

### UX-12 · Minor · Two scrollbars on long lists

*Where:* Org Positions, Users

*Observed:* The page (main) and the table container both scroll, so two scrollbars sit side by side and the mouse wheel scrolls different things depending on where the pointer is.

*Recommendation:* Choose one model and use it everywhere. Either the page scrolls with a sticky table header, or the table fills the viewport (scrollHeight="flex", as CLAUDE.md specifies) and the page doesn’t scroll.

<a id="ux-13"></a>

### UX-13 · Minor · Row actions are unlabeled icons, and some aren’t guessable

*Where:* Organization Structure, Roles, Lookups, Workflows, Users

*Observed:* Organization Structure shows four icons per row: add child, edit, manage head (a crown) and deactivate. Their meaning appears only in a hover tooltip, which wraps mid-word at the screen edge (“Mana / ge Head”). None of the buttons has an accessible name. A deactivate icon also appears on system roles and on the signed-in user’s own row.

*Recommendation:* Keep one or two frequent icons and put the rest in a ⋯ menu with text labels. Give every icon button an aria-label, place tooltips to the left near the right edge, and hide or disable actions that aren’t allowed.

<a id="ux-14"></a>

### UX-14 · Minor · System codes appear where people expect plain words

*Where:* Workflows, Tasks, Committees, Lookups, Roles, Organization Structure

*Observed:* Examples: DOCUMENT_REQUEST, SINGLE, POSITION_FIXED, ROLE_BASED, MONTHLY, IN_PROGRESS; Unit Type shown as “administration” and “department”; a Key column of developer identifiers (committee_type); and permission names such as add_member, manage_system and view_all.

*Recommendation:* Show translated labels from the lookup and i18n files (“Fixed position”, “Monthly”, “In progress”). Put technical keys behind a “Show system keys” toggle for administrators, and give each permission a readable name and a one-line description.

<a id="ux-15"></a>

### UX-15 · Minor · Bilingual names are laid out differently from table to table

*Where:* Organization Structure vs Roles, Workflows, Org Positions

*Observed:* Organization Structure puts the Arabic name in brackets inside the “Name (English)” column. Other tables use a separate Arabic column whose text is right-aligned inside a left-to-right table, leaving a wide gap next to the English name.

*Recommendation:* Use one pattern: the name in the user’s current language as the main line, and the other language as a smaller, muted second line in its own text direction.

<a id="ux-16"></a>

### UX-16 · Minor · Colored pills are used so often they stop meaning anything

*Where:* Lookups, Roles, Org Positions, Workflows

*Observed:* Green is used for both “Active” and “Yes”. Org Positions shows a blue “Yes” for Single Assignee and an orange “Yes” for Head-Conferring, and leaves No blank, while Lookups shows No as a grey pill. Nearly every row is green, so nothing stands out.

*Recommendation:* Save colored tags for states that need attention (Inactive, Draft, Overdue, Missing head). Show booleans as plain text or a check mark, and let users filter out inactive records instead of labelling every row Active.

<a id="ux-17"></a>

### UX-17 · Minor · Roles list says every role has 0 permissions

*Where:* /roles

*Observed:* The column header reads “0 permissions” and every row shows 0, but the Quality Manager permission matrix has more than 35 permissions checked. In the code, the header passes count: 0 to a pluralised translation key, and the list response doesn’t include permissions, so role.permissions?.length is always 0.

*Recommendation:* Change the header to “Permissions” and return a permission count from the list endpoint. In the matrix, add “Select all” per module, and grey out modules that aren’t built or licensed yet (Audits, KPI, Billing).

## Forms, dialogs & record pages

<a id="ux-18"></a>

### UX-18 · Minor · Add Unit: Save is hidden below the fold, and Unit Type can’t be set

*Where:* Organization Structure → Add Unit

*Observed:* The dialog is about 550 px tall even when the screen has room. Its body scrolls, and Save and Cancel scroll with it instead of staying in a fixed footer. The table has a Unit Type column, but the form (org-unit-form) has no Unit Type field.

*Recommendation:* Give the dialog a sticky footer and a taller maximum height (about 85vh), or a two-column layout. Add a Unit Type field that uses the org_unit_type lookup.

<a id="ux-19"></a>

### UX-19 · Minor · The user record is one long form with four separate save buttons

*Where:* /users/:id

*Observed:* Profile fields, Out of Office, Two-Factor Authentication and roles are stacked in one half-width column, each with its own Save, Enable or Assign button, so it isn’t clear what each button saves. The roles section is titled “Assigned Users” when it lists roles. The page is indented more than every other page.

*Recommendation:* Split the record into tabs (Profile · Roles & access · Out of office · Security). Use one save per tab, or a sticky bar that appears when there are unsaved changes. Rename the section to “Assigned roles” and use the standard page indent.

<a id="ux-20"></a>

### UX-20 · Minor · Plain text boxes where proper pickers are needed

*Where:* Working Calendar, User record, Organization Profile

*Observed:* Working days use unstyled native checkboxes. Working hours are typed as text (“08:00”). The Out-of-office From/To and “Until” fields are plain text boxes. Country is typed as a code (“SA”). The Logo field asks users to “paste an S3 key”.

*Recommendation:* Use a PrimeNG toggle-button group for days, time and date pickers (with Hijri display where the user prefers it), and a searchable country list. Hide the Logo field until file upload works.

<a id="ux-21"></a>

### UX-21 · Minor · Forms give no feedback on mistakes

*Where:* Login; dialogs with disabled Save

*Observed:* Clicking “Log In” with every field empty does nothing: no message and no highlighted fields. In dialogs, Save is disabled with nothing to explain why.

*Recommendation:* Let the user submit, then show inline errors and move focus to the first invalid field. Where Save stays disabled, show which required fields are still missing.

<a id="ux-22"></a>

### UX-22 · Minor · Loading states are blank, or show an empty list that isn’t empty

*Where:* App start, Public Holidays, lists

*Observed:* A full page load shows a blank light-grey screen for 2–3 seconds. Public Holidays shows “No public holidays defined for this year” while its spinner is still running. Lists dim under an overlay spinner. There are no skeleton loaders anywhere in the codebase.

*Recommendation:* Add a branded splash in index.html and skeleton rows for tables and cards. Don’t show an empty-state message until loading has finished.

## Accessibility, language & devices

<a id="ux-23"></a>

### UX-23 · Major · The accessibility baseline is below WCAG 2.2 AA

*Where:* App-wide

*Observed:* The whole frontend has one aria-label. The topbar menu, bell and profile buttons and every row icon button have no accessible name. Form labels in #718096 on the #F4F7FA page background measure 3.73:1 (“From”, “To”, “Year”), and 4.02:1 on white, below the 4.5:1 minimum. Notification items can’t be reached by keyboard.

*Recommendation:* Set an AA baseline before the demo: accessible names on all icon buttons, a darker secondary text token (at least #5A6B82 for 4.5:1 on the page background), keyboard access for popovers and menus, and an automated axe check in CI. Government and healthcare buyers in the GCC often ask for WCAG AA.

<a id="ux-24"></a>

### UX-24 · Minor · Dates are ambiguous and formatted differently on different pages

*Where:* Notifications, Tasks, Users vs Committees

*Observed:* Notifications, Tasks and Users show “9/10/26, 12:45 PM” (US month/day/year), which a GCC reader takes as 9 October. Committees show “Sep 7, 2026”.

*Recommendation:* Use one date pipe with the tenant locale and an unambiguous format (“10 Sep 2026, 12:45”), plus the Hijri option from CLAUDE.md. Show due dates relative to now where it helps.

<a id="ux-25"></a>

### UX-25 · Minor · No layout for tablet or phone

*Where:* App shell (code review)

*Observed:* The sidebar is a fixed 260 px (72 px collapsed), the layout has no breakpoints, and responsive breakpoints appear on only 5 elements in the app, all of them card grids. The collapsed state isn’t remembered. Tablets are common on ward rounds and during audits. I couldn’t check this in the browser because the window could not be resized.

*Recommendation:* Collapse the sidebar automatically below 1280 px and make it an off-canvas drawer below 1024 px. Let wide tables scroll horizontally with the first column pinned, or turn rows into cards, and remember the collapsed state.

<a id="ux-26"></a>

### UX-26 · Improvement · The login page has no branding or language choice, and asks for an organization slug

*Where:* /login

*Observed:* The page has no logo, no product name and no English/Arabic switch. The Password field is narrower than the others, and its eye icon sits outside the field. The Organization field expects a URL slug (“al-nakheel”) that most staff won’t know.

*Recommendation:* Add the logo and a language switch, and give the password field the same width with the icon inside it. Resolve the organization from the subdomain (already planned in CLAUDE.md) or remember the last one used, so users only type their email and password.

## How this was reviewed

- Read CLAUDE.md for purpose, audience, build sequence and design tokens.
- Walked the app in Chrome at 1864×927 CSS px as Dr. Hessa Al-Dosari (Organization Administrator). No records were created, edited or deleted.
- Supported by a read-only frontend source scan and computed contrast ratios.
- Judged against Nielsen’s heuristics, WCAG 2.2 AA and enterprise-SaaS conventions.
- Not covered: live Arabic/RTL, tablet/phone widths (UX-25 is based on code only), non-admin roles, Super Admin portal, email flows, destructive confirmations.

**Screens walked:** Login, Organization Structure + Add Unit dialog, Notification panel, Profile menu, Working Calendar, Public Holidays, Lookup categories, Lookup values, Roles, Permission matrix, Workflow templates, Workflow stages & transitions, Org Positions, Committees list, Committee detail, My Tasks, Unassigned Tasks, Users list, User record, Transfer User wizard, Admin Settings hub, Organization Profile, AI Settings, Task SLA & Escalation.
